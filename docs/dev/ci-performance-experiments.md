# CI performance experiments

This document records UDS Core pull request CI timing experiments, test coverage, and decisions. Use the same workflow and matrix when comparing runs so timing changes remain meaningful.

## Goals

The CI optimization work has three goals:

- Reduce the time to the first useful failure signal.
- Preserve the current pull request test coverage and confidence.
- Avoid increasing CI spend.

The primary timing metric is the time from workflow start until the relevant job reports a result. The overall workflow duration remains important, but it should not replace fast independent feedback from linting, unit tests, and routing.

## Baseline

The baseline comes from the successful [Filter workflow run for PR #2959](https://github.com/defenseunicorns/uds-core/actions/runs/34626511558). The workflow ran for approximately 37 minutes and 17 seconds.

The baseline timings were:

| Job or phase | Observed timing |
| --- | ---: |
| Lint | 1m 55s |
| Autogenerated checks | 2m 28s |
| Unit test job | 4m 04s |
| Select Jobs became available | About 4m 11s after workflow start |
| Core jobs began | About 4m 20s after workflow start |
| Core install | About 22m |
| Core upgrade | About 32m |
| Core values test | About 22m |

The original unit command ran 67 files and 1,238 tests. The values suites accounted for 9 files and 176 tests within that total.

## Experiments

### Run independent routing and checks

The `Select Jobs` job no longer waits for linting, autogenerated checks, or unit tests. Unit tests and values tests also run as separate jobs.

Result from the [artifact experiment run](https://github.com/defenseunicorns/uds-core/actions/runs/34634358634):

- `Select Jobs` completed in 8 seconds instead of waiting about 4 minutes.
- Unit tests completed in a 37-second job and ran 58 files with 1,062 tests.
- Values tests completed independently in 4 minutes and 55 seconds and ran 9 files with 176 tests.
- The two test jobs together preserved the original 67-file, 1,238-test coverage.

Decision: keep this change. It improves early feedback and preserves the existing unit and values test coverage.

### Reuse a prebuilt Core artifact

The experiment built the Core package and bundle once, uploaded them, and downloaded them in the Core test jobs.

Observed costs and behavior:

- The build job took 4 minutes and 8 seconds.
- The artifact upload took 2 minutes and 6 seconds.
- The artifact was approximately 4.557 GB.
- Consumer download times ranged from 40 seconds to 4 minutes and 21 seconds.
- Core consumers began about 4 minutes and 25 seconds after workflow start, which was effectively the same as the baseline.
- The install test later failed because the prebuilt path skipped the root dependency installation required by `test/vitest/vitest.setup.js`, which imports `pepr`.

The run used only the `upstream` flavor and temporarily disabled other matrix jobs, so it does not provide a full-matrix comparison. It does show that artifact transfer removes the intended scheduling benefit and adds substantial data movement.

Decision: do not use a shared Core artifact for pull request CI. Remove the artifact build, upload, download, and prebuilt task paths.

## Current implementation

The current branch keeps the independent routing and test split, while restoring the full pull request matrix. Each Core and layer test job builds its own local package or bundle on its own runner.

The current implementation no longer contains the experimental `build-core`, `core_artifact`, or `use_prebuilt` paths.

## Next measurement

The next comparable run should use the restored full matrix and measure these values against the baseline:

- Time to `Select Jobs` completion.
- Time to unit test completion.
- Time to values test completion.
- Time until the first Core install, upgrade, and values jobs begin.
- Duration of each Core and layer matrix job.
- Total workflow duration.
- Aggregate runner time, where available.

Record any failures separately from timing improvements. A faster run that cancels or omits matrix coverage does not establish an equivalent CI improvement.
