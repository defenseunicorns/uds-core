UDS Core marks each Package-managed Keycloak client with the Kubernetes UID of its Package. The operator verifies this marker before updating or deleting a client. A current Package must be the only Package whose spec claims a client ID before the operator creates or updates it. Authservice uptime checks generate `<clientId>-probe` IDs, which follow the same ownership rules.

## Resolve an ownership conflict

<Steps>

1. Find the Package UID, declared SSO IDs, generated probe IDs, and recorded client IDs:

   ```bash
   uds zarf tools kubectl get packages -A -o yaml
   ```

   A probe ID is generated when an uptime expose entry has nonempty check paths and matches an Authservice SSO entry. Include those IDs when checking for another Package with the same client ID.

2. In the Keycloak Admin Console, select the `uds` realm and inspect the client ID and its Package UID marker. Do not change the marker to make reconciliation succeed.

3. If another current Package claims an ID whose Keycloak marker belongs to a former Package that has removed it from its spec, let the former Package finish cleanup. If the former Package's Keycloak deletion succeeded but its status update failed, a retry treats cleanup as complete after verifying that its status records the old ID and the new marker UID is the sole current claimant. It leaves the new Package's client untouched. If those checks fail, resolve the ownership conflict before retrying.

</Steps>

## Legacy clients

Clients created before UID markers existed are adopted during reconciliation only when one current Package claims the ID, that Package alone records the ID in `status.ssoClients`, and the client has a recognized operator-managed configuration. A matching configuration shape shows that the operator managed the client; it does not identify its Package owner. If any evidence is missing or another Package records the ID, the operator leaves the client unchanged and fails reconciliation.

During cleanup, an unmarked client can be removed after its SSO entry leaves the spec if exactly one live Package records the ID in `status.ssoClients`, no other current Package claims the ID, and the Keycloak client itself has one recognized operator configuration: the SSO groups attribute, or a probe service account with one audience mapper whose target matches the `<clientId>-probe` name. The operator verifies the exact client UUID and deletes it without adding an owner marker. Ambiguous or unsupported legacy clients require administrator review.

## Recover a stale or mismatched client

Review the Package UID and status alongside the client configuration and any available change records. If the client belongs to a deleted or recreated Package and no current Package needs it, remove the stale client from the `uds` realm and let the current Package reconcile it. This creates a new client secret; update dependent workloads that use the old secret.

If the owner is another live Package, resolve duplicate or incorrect Package configuration first. If a Package remains in `Retrying`, `Failed`, or `RemovalFailed`, keep its finalizer in place while resolving the ownership or Keycloak API error, then retry reconciliation or deletion.
