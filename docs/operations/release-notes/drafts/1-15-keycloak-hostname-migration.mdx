UDS Core restores request-based public Keycloak URLs so one realm can serve multiple SSO hostnames. The upgrade also removes the exact `uds.frontendUrl` value generated by Identity Config 0.32.1. This is a focused draft excerpt; merge it into the complete Core 1.15 release notes before publication.

### ⚠ Breaking changes

| Change                                                                     | Impact                                                                                                                                  | Action required                                                                                                             |
| -------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Identity Config removes the generated `uds.frontendUrl`                    | A fixed URL that exactly matched `https://sso.<UDS_DOMAIN>` is removed, including when an operator intentionally chose that same value. | Reapply the fixed URL after upgrading if you still need it.                                                                 |
| Direct Keycloak backchannel access is limited to Core and Fleet namespaces | Custom workloads that call the Keycloak service directly may lose access.                                                               | Add an `additionalNetworkAllow` rule for each trusted workload that requires direct access. Avoid wildcard namespace rules. |

### Notable features

- **Alternate SSO hostnames:** Keycloak derives public URLs from each request, allowing alternate SSO hosts to use discovery and issuer validation.
- **One-time realm migration:** The migration removes only the exact generated UDS URL from databases that ran Identity Config 0.32.1. It preserves `master.frontendUrl` and any differing `uds.frontendUrl`.

## Upgrade considerations

### Manual realm changes

The migration runs once. If it preserves a differing or old `uds.frontendUrl` because it cannot match the current `UDS_DOMAIN`, correcting `UDS_DOMAIN` later will not retry the migration. Use the Keycloak Admin Console to review or repair the value:

<Steps>

1. **Review the UDS realm URL**

   Open **Realm settings** for the `uds` realm and inspect **Frontend URL**.

2. **Choose the intended URL**

   Clear **Frontend URL** to restore request-based URLs, or set the fixed URL you want Keycloak to use. Save the realm settings. The completed migration marker does not prevent this manual change.

3. **Restore an intentional generated URL**

   If you intentionally used `https://sso.<UDS_DOMAIN>` as a fixed URL, set it again after the migration. The migration cannot distinguish that choice from the value written by Identity Config 0.32.1.

4. **Check the master realm after an admin-domain change**

   The migration leaves `master.frontendUrl` unchanged. If you change `UDS_ADMIN_DOMAIN`, inspect the `master` realm's **Frontend URL**. Update it to the intended admin URL if it points to the old generated domain, or clear it if you want request-based URLs. Preserve any custom value you still need.

5. **Verify discovery**

   Open `https://sso.<UDS_DOMAIN>/realms/uds/.well-known/openid-configuration` and confirm the `issuer` uses the requested host. Repeat through each alternate SSO hostname.

</Steps>

If a custom workload needs direct access to the Keycloak service, add a narrowly scoped `additionalNetworkAllow` rule to the Keycloak chart values. The default allowlist retains Core control-plane and Fleet callers.
