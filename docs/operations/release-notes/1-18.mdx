UDS Core 1.18 updates Istio and Prometheus Operator. If your upgrade includes the Identity Config client ownership change, review the migration steps before upgrading.

### ⚠ Breaking changes

Review this change before upgrading to a build that includes the Identity Config update.

| Change | Impact | Action required |
| --- | --- | --- |
| Keycloak client ownership | Service accounts enrolled in the UDS Client Policy can manage only clients whose `created-by` attribute matches their Keycloak client ID. Client roles inherit that ownership. | Follow the [client ownership migration](#identity-config-updates-client-ownership) for existing clients that enrolled service accounts must continue managing. |

### Notable features

This release includes these updates:

- **Keycloak:** Disables hardware-accelerated Base64 encoding and decoding. UDS Core 1.17.2 also includes this fix ([#3240](https://github.com/defenseunicorns/uds-core/pull/3240)).
- **Package metadata:** UDS Core packages now link to their source repository ([#3220](https://github.com/defenseunicorns/uds-core/pull/3220)).

### Dependency updates

The following versions change from UDS Core 1.17.0. UDS Core 1.17.2 already includes these updates.

| Package | Previous | Updated |
| --- | --- | --- |
| Istio (upstream and Unicorn) | 1.31.2 | [1.32.0](https://github.com/istio/istio/releases/tag/1.32.0) |
| Prometheus Operator (upstream) | 0.95.1 | [0.95.2](https://github.com/prometheus-operator/prometheus-operator/releases/tag/v0.95.2) |

## Upgrade considerations

### Identity Config updates: client ownership

This migration applies to builds that include the [Identity Config ownership change](https://github.com/defenseunicorns/uds-identity-config/pull/963), which is planned for UDS Core 1.18.0. The UDS Client Policy enrolls the UDS Operator (`uds-operator`) and `uds-fleet-admin` by default. An enrolled service account follows the ownership rule even if it has the `realm-admin` role.

Use these examples to decide which existing clients need an ownership update.

| Scenario | Example | Before upgrading |
| --- | --- | --- |
| The UDS Operator registers a new SSO client from a `Package` CR after the upgrade. | A `Package` sets `spec.sso[].clientId` to `my-app`. When the UDS Operator creates that client, the policy sets `created-by` to `uds-operator`. | No action for a client that does not exist yet. |
| The UDS Operator already manages a Package SSO client with the correct owner. | The Grafana `Package` uses `uds-core-admin-grafana` as its SSO client ID. If `created-by` is already `uds-operator`, the operator can continue reconciling it. | Verify the existing value. |
| A Keycloak administrator creates a client for the UDS Operator to manage. | An administrator registers `my-app` through the Keycloak Admin Console before adding that client ID to a `Package` CR. | Verify the handoff and set `created-by` to `uds-operator` before the operator reconciles it on the upgraded system. |

Before upgrading, assign the intended service account's client ID to each affected client.

<Steps>

1. **Identify the owner**

   Pause affected automation and back up each client's `created-by` attribute. Verify the enrolled service account's `clientId`. A client's name alone cannot establish its owner.

2. **Assign ownership through the admin gateway**

   Set `KEYCLOAK_TOKEN` to an access token from your usual administrator sign-in. Use an unenrolled client and an account with administrator access to the `uds` realm. Replace the admin gateway URL and client IDs below. Run the script with Bash, `curl`, and `jq`. Keep TLS verification enabled and supply your trusted CA if needed.

   ```bash
   set -euo pipefail
   : "${KEYCLOAK_TOKEN:?Set KEYCLOAK_TOKEN to an administrator access token}"
   CLIENTS_URL='https://keycloak.admin.uds.dev/admin/realms/uds/clients'
   TARGET_CLIENT_ID='<client-to-migrate>'
   OWNER_CLIENT_ID='<owning-application-clientId>'

   keycloak() {
     curl --fail-with-body --silent --show-error \
       -H "Authorization: Bearer $KEYCLOAK_TOKEN" "$@"
   }

   CLIENT_UUID=$(keycloak --get --data-urlencode "clientId=$TARGET_CLIENT_ID" "$CLIENTS_URL" \
     | jq -er --arg id "$TARGET_CLIENT_ID" '
       map(select(.clientId == $id))
       | if length == 1 then .[0].id | select(type == "string" and length > 0)
         else error("Expected exactly one matching client") end')
   CLIENT_URL="$CLIENTS_URL/$CLIENT_UUID"

   # Keycloak disables Authorization Services if the update omits this field.
   AUTHZ_ENABLED=$(keycloak "$CLIENT_URL" | jq '.authorizationServicesEnabled // false')
   jq -n --arg owner "$OWNER_CLIENT_ID" --argjson enabled "$AUTHZ_ENABLED" \
     '{authorizationServicesEnabled: $enabled, attributes: {"created-by": $owner}}' \
     | keycloak -X PUT -H 'Content-Type: application/json' --data-binary @- "$CLIENT_URL"

   # Expect true.
   keycloak "$CLIENT_URL" | jq -e --arg owner "$OWNER_CLIENT_ID" --argjson enabled "$AUTHZ_ENABLED" \
     '.attributes["created-by"] == $owner and (.authorizationServicesEnabled // false) == $enabled'
   ```

   This update changes ownership while preserving the existing Authorization Services state, unrelated client settings, and client UUID. Client roles inherit this ownership and need no separate migration.

3. **Verify after upgrading and resume automation**

   Use the intended manager to read and update a migrated client and manage a disposable client role. Verify that another service account enrolled in the policy cannot access that role. Delete the disposable role, then resume automation. If needed, use a Keycloak administrator authenticated through an unenrolled client to restore the saved ownership values.

</Steps>
