UDS Packages expose configuration through [Zarf Values](/reference/configuration/zarf-values/), a structured mechanism for passing Helm Chart values at deploy time. In general, expose most non-sensitive chart values and restrict values that would break package integrity or weaken security, such as image references, ingress, or security settings.

> [!NOTE]
> This page uses [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt) terminology.

## Values structure

Define the top-level `values` key in your root `zarf.yaml` and reference:

- A `zarf-values.yaml` for defaults
- A `zarf-values.schema.json` for validation

The schema **MUST** follow [JSON Schema](https://json-schema.org/) and you **SHOULD** use `uds zarf dev generate-schema` to generate it from the package definition, chart values, and value mappings.

Add value mappings (`sourcePath` and `targetPath`) near your chart definitions (commonly in `common/zarf.yaml`), keeping mappings as flat as practical and exposing the highest sensible node in the values tree.

If individual mappings become unwieldy, consider mapping higher-level nodes and using `excludePaths` to omit settings that deployers should not override.

Use values for package configuration, retaining `###ZARF_VAR_<NAME>###` in ordinary `valuesFiles` only when an existing variable must remain compatible. Declare any such variable in the package definition and use `templatedValuesFiles` with `.Variables.<NAME>` when explicit package values must take precedence over the variable or need a computed fallback. Because Zarf substitutes variable tokens before evaluating Go templates, keep those phases separate.

> [!NOTE]
> You **SHOULD** expose the UDS integration settings your application supports through chart values and map them to normalized package values, reusing common names and groupings so deployers can configure packages consistently without editing Helm templates.
>
> These settings **SHOULD** live alongside the UDS-specific resources they configure, either in a separate `config` chart when you use an upstream application chart or directly in a local application chart tailored for UDS.
>
> Use the following conventions where they apply, exposing only the options your integration supports rather than adding every setting to every application:
>
> | Values pattern | Guidance |
> | --- | --- |
> | `domain` | Set the base domain for application URLs and SSO redirect URIs. |
> | `subdomain`, `gateway` | Set the exposed host prefix and Istio gateway in `Package.spec.network.expose`, using service-specific host keys when the application exposes multiple services. |
> | `additionalNetworkAllow` | Append deployment-specific rules to `Package.spec.network.allow` without replacing required application rules, defaulting the list to `[]` and scoping additions to the necessary traffic. |
> | `sso.enabled`, `sso.protocol` | Configure SSO and the generated `Secret` the application consumes, exposing only supported protocols and keeping SSO enabled by default when the package requires it. |
> | `sso.requiredGroups`, `sso.adminGroups`, `sso.defaultClientScopes` | Configure login restrictions and client scopes alongside application-specific administrator-group mappings. |
> | Dependency groups such as `postgres`, `redis`, and `storage` | Group connection settings and network-rule inputs such as `internal`, `namespace`, `selector`, and `port` to support the application's in-cluster or external dependency options. |
>
> You **SHOULD** define shared settings once at the package level and map them into every chart that consumes them so the application and its UDS resources stay consistent. For example, a dependency override should update both the application's connection configuration and the config chart's network rules, just as a hostname override should keep application URLs and SSO redirects aligned.
>
> Document supported keys and defaults in the package `documentation` and validate them through its values schema, following the chart-mapping and schema examples below.
>
> Reference the [UDS Reference Package](https://github.com/uds-packages/reference-package/blob/main/chart/values.yaml) for an example of how these values can be used in practice and [UDS `Package` CR specification](/reference/operator-and-crds/packages-v1alpha1-cr/) for the resources these values configure.

## Example configuration

The following nginx example defines package values and maps them into application and UDS config charts within the Zarf package definition:

```yaml title="common/zarf.yaml"
kind: ZarfPackageConfig
metadata:
  name: nginx
  description: UDS Common Nginx Example

components:
  - name: nginx
    required: true
    charts:
      - name: uds-nginx-config
        namespace: nginx
        version: 0.1.0
        localPath: ../chart
        values:
          - sourcePath: .global
            targetPath: .
      - name: nginx
        version: 0.1.0
        namespace: nginx
        localPath: ../src/nginx
        valuesFiles:
          - ../values/common-values.yaml
        values:
          - sourcePath: .nginx
            targetPath: .
            excludePaths:
              - .nginx.image
              - .nginx.imagePullSecrets
              - .nginx.ingress
              - .nginx.podSecurityContext
              - .nginx.securityContext
              - .nginx.livenessProbe
              - .nginx.readinessProbe
```

The first mapping passes the package-level `global.domain` value to the `uds-nginx-config` chart as `domain`, while the second passes the application values to the nginx chart.

The root `zarf.yaml` declares the defaults and schema files, imports the common component, and adds flavor-specific values and images:

```yaml title="zarf.yaml"
kind: ZarfPackageConfig
metadata:
  name: nginx
  description: UDS Nginx Example Package

values:
  files:
    - zarf-values.yaml
  schema: zarf-values.schema.json

components:
  - name: nginx
    required: true
    description: Deploy nginx with upstream images
    import:
      path: common
    only:
      flavor: upstream
    charts:
      - name: nginx
        valuesFiles:
          - values/upstream-values.yaml
    images:
      - nginx:1.30.0
```

The `zarf-values.yaml` provides defaults that deployers can override:

```yaml title="zarf-values.yaml"
global:
  domain: uds.dev

nginx:
  replicaCount: 1
  service:
    type: ClusterIP
    port: 8080
  resources: {}
  autoscaling:
    enabled: false
    minReplicas: 1
    maxReplicas: 100
    targetCPUUtilizationPercentage: 80
  volumes: []
  volumeMounts: []
  nodeSelector: {}
  tolerations: []
  affinity: {}
```

The `zarf-values.schema.json` validates the defaults above:

```json title="zarf-values.schema.json"
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "type": "object",
  "additionalProperties": false,
  "properties": {
    "global": {
      "type": "object",
      "additionalProperties": false,
      "properties": {
        "domain": {
          "type": "string"
        }
      }
    },
    "nginx": {
      "type": "object",
      "additionalProperties": false,
      "properties": {
        "replicaCount": {
          "type": "integer",
          "minimum": 0
        },
        "service": {
          "type": "object",
          "additionalProperties": false,
          "properties": {
            "type": { "type": "string" },
            "port": {
              "type": "integer",
              "minimum": 1,
              "maximum": 65535
            }
          }
        },
        "resources": { "type": "object" },
        "autoscaling": { "type": "object" },
        "volumes": { "type": "array", "items": { "type": "object" } },
        "volumeMounts": { "type": "array", "items": { "type": "object" } },
        "nodeSelector": { "type": "object" },
        "tolerations": { "type": "array", "items": { "type": "object" } },
        "affinity": { "type": "object" }
      }
    }
  }
}
```
