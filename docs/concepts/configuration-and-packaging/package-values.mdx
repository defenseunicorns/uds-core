UDS Packages expose configuration through [Zarf Values](/reference/configuration/zarf-values/), a structured mechanism for passing Helm chart values at deploy time. Expose deployment-specific configuration and restrict overrides of platform-critical settings that could break UDS integration or weaken security, such as image references, ingress configuration, or security settings.

> [!NOTE]
> This page uses [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt) terminology.

## Values structure

Define the top-level `values` key in your root `zarf.yaml` and reference:

- A `zarf-values.yaml` for defaults
- A `zarf-values.schema.json` for validation

The schema **MUST** follow [JSON Schema](https://json-schema.org/) and you **SHOULD** use `uds zarf dev generate-schema` to generate it from the package definition, chart values, and value mappings.

Add value mappings (`sourcePath` and `targetPath`) near your chart definitions (commonly in `common/zarf.yaml`), keeping mappings as flat as practical and exposing the highest sensible node in the values tree.

If individual mappings become unwieldy, consider mapping higher-level nodes and using `excludePaths` to omit settings that deployers should not override.

Use values for package configuration, retaining `###ZARF_VAR_<NAME>###` in ordinary `valuesFiles` only when an existing variable must remain compatible. Declare any such variable in the package definition and use `templatedValuesFiles` with `.Variables.<NAME>` when explicit package values must take precedence over the variable or need a computed fallback. Because Zarf substitutes variable tokens before evaluating Go templates, keep those phases separate.

## UDS integration values

Your package **SHOULD** provide these controls so deployers can adapt it to their environment:

- `subdomain`: For externally exposed services, expose a top-level package value for the host prefix in `Package.spec.network.expose` so deployers can avoid hostname conflicts with other applications. Use service-specific hostname values when you expose multiple services, and keep application URLs and SSO redirects aligned with hostname overrides.
- `additionalNetworkAllow`: Let deployers add environment-specific rules to `Package.spec.network.allow`. Default to `[]` and append these rules without replacing the package's required rules.

Use common names and groupings for other supported integration settings:

| Values pattern | Guidance |
| --- | --- |
| `domain` | Expose the base domain when the chart or application needs it for application URLs or SSO redirect URIs. |
| `sso.enabled`, `sso.protocol` | Configure SSO and the generated `Secret` the application consumes, exposing only supported protocols and keeping SSO enabled by default when the package requires it. |
| `sso.requiredGroups`, `sso.adminGroups`, `sso.defaultClientScopes` | Configure login restrictions and client scopes alongside application-specific administrator-group mappings. |
| Dependency groups such as `postgres`, `redis`, and `storage` | Group connection settings and network-rule inputs such as `internal`, `namespace`, `selector`, and `port` to support the application's in-cluster or external dependency options. |

These settings **SHOULD** live alongside the UDS resources they configure, either in a separate `config` chart when you use an upstream application chart or directly in a local application chart tailored for UDS.

You **SHOULD** define shared settings once at the package level and map them into every chart that consumes them. For example, a dependency override should update both the application's connection configuration and the config chart's network rules.

Document supported keys and defaults in the package `documentation` and validate them through its values schema.

Reference the [UDS Reference Package](https://github.com/uds-packages/reference-package/blob/main/chart/values.yaml) for an example and the [UDS `Package` CR specification](/reference/operator-and-crds/packages-v1alpha1-cr/) for the resources these values configure.

## Example configuration

The following nginx example defines package values and maps them into application and UDS config charts within the Zarf package definition. The chart directories and chart-specific values files are not included; this example focuses on the package values configuration:

```yaml title="common/zarf.yaml"
kind: ZarfPackageConfig
metadata:
  name: nginx
  description: UDS Common Nginx Example

components:
  - name: nginx
    required: true
    charts:
      - name: uds-nginx-config
        namespace: nginx
        version: 0.1.0
        localPath: ../chart
        values:
          - sourcePath: .global
            targetPath: .
          - sourcePath: .subdomain
            targetPath: .subdomain
          - sourcePath: .additionalNetworkAllow
            targetPath: .additionalNetworkAllow
      - name: nginx
        version: 0.1.0
        namespace: nginx
        localPath: ../src/nginx
        valuesFiles:
          - ../values/common-values.yaml
        values:
          - sourcePath: .nginx
            targetPath: .
            excludePaths:
              - .nginx.image
              - .nginx.imagePullSecrets
              - .nginx.ingress
              - .nginx.podSecurityContext
              - .nginx.securityContext
              - .nginx.livenessProbe
              - .nginx.readinessProbe
```

The config chart mappings pass `global.domain` as `domain` and the top-level `subdomain` and `additionalNetworkAllow` values to matching chart keys. The `.nginx` mapping passes the application values to the nginx chart.

The root `zarf.yaml` declares the defaults and schema files, imports the common component, and adds flavor-specific values and images:

```yaml title="zarf.yaml"
kind: ZarfPackageConfig
metadata:
  name: nginx
  description: UDS Nginx Example Package

values:
  files:
    - zarf-values.yaml
  schema: zarf-values.schema.json

components:
  - name: nginx
    required: true
    description: Deploy nginx with upstream images
    import:
      path: common
    only:
      flavor: upstream
    charts:
      - name: nginx
        valuesFiles:
          - values/upstream-values.yaml
    images:
      - nginx:1.30.0
```

The `zarf-values.yaml` provides defaults that deployers can override:

```yaml title="zarf-values.yaml"
subdomain: nginx
additionalNetworkAllow: []

global:
  domain: uds.dev

nginx:
  replicaCount: 1
  service:
    type: ClusterIP
    port: 8080
  resources: {}
  autoscaling:
    enabled: false
    minReplicas: 1
    maxReplicas: 100
    targetCPUUtilizationPercentage: 80
  volumes: []
  volumeMounts: []
  nodeSelector: {}
  tolerations: []
  affinity: {}
```

### Override values at deployment

After building a package with these mappings, you can override supported values without editing or rebuilding the package. For example, save this deployment-specific override alongside the built package:

```yaml title="deployment-values.yaml"
nginx:
  replicaCount: 2
```

Deploy to your UDS Core cluster with the override file. Replace `path/to/zarf-package-nginx.tar.zst` with your built package archive:

```bash
uds zarf package deploy path/to/zarf-package-nginx.tar.zst \
  --values deployment-values.yaml
```

The override changes the package default `nginx.replicaCount` from `1` to `2`. The `sourcePath: .nginx` mapping passes it to the nginx chart as `replicaCount: 2`, which sets the application's replica count. Keep package defaults in `zarf-values.yaml` and deployment-specific overrides in the separate file. See [Zarf Values](https://docs.zarf.dev/ref/examples/values-templating/) for merge and precedence behavior.
